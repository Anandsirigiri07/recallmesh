# RECALLMESH — Milestone 4B.4: Action Plans & Governed Response Workflow

## 1. Executive Summary & Objective

Milestone 4B.4 implements the complete **Action Plans & Governed Response Workflow** for the RECALLMESH food traceability and incident surveillance platform. This workflow bridges offline graph traversal insights with auditable, human-governed containment responses under FSMA 204 (Food Safety Modernization Act Section 204).

The system generates evidence-backed containment plans from genuine FalkorDB property graph traversals, enforces strict human operator approval gates, records immutable audit trails in FalkorDB, and renders an authoritative user interface matching the Google Stitch design specification.

---

## 2. Core Capabilities & Architecture

### A. Data-Driven Plan Recommendations
- **Dynamic Traversal Grounding**: Containment plans are computed on-the-fly via graph traversal starting from the suspect raw lot code (e.g., `LOT-CUM-2026-088`). The graph traces:
  - Upstream supplier origin (`Supplier` node, e.g., `Apex Spice Co.`)
  - Intermediate transformation events (`TransformationEvent`, e.g., `TR-2026-001`)
  - Downstream finished product lots (`FinishedLot`, e.g., `FL-SALSA-101`, `FL-SALSA-103`)
  - Outbound shipments and distribution destinations (`Shipment`, `Facility`, e.g., `SHIP-8821`, `Austin Central Distribution`)
- **Relationship Classification**:
  - `CONFIRMED_AFFECTED`: Explicit graph edge verification linking the contaminated lot to a finished lot or shipment.
  - `EVIDENCE_GAP`: Missing link or unverified CTE (Critical Tracking Event), such as missing recipe or receiving records, prompting simulated supplier evidence collection rather than unwarranted physical stoppage.
- **Zero Hardcoding**: Action targets, facilities, lot codes, and supplier names are resolved dynamically from graph query results.

### B. Human-in-the-Loop Governance Gates
- **Status Lifecycle**: Every action candidate transitions through explicit persisted states:
  - `PROPOSED` (or `Draft`): Candidate recommendation generated by the response planner.
  - `PENDING_REVIEW`: Returned by reviewer requesting additional investigation or parameter adjustments.
  - `APPROVED`: Fully signed off by an authorized human operator with mandatory rationale.
  - `REJECTED`: Blocked or dismissed by the operator with justification.
  - `COMPLETED`: Containment action simulated and recorded as complete.
- **Mandatory Approver Identity & Rationale**:
  - The API rejects any status change where `actor` or `rationale` is missing or whitespace-only (HTTP 422 / 403).
  - Approver identities are **never fabricated**; default or missing actors are strictly blocked.
- **Audit Trail Recording**: Every state transition creates an immutable `:AuditEvent` node in FalkorDB linked to the action ID, capturing:
  - `event_id` (e.g., `AUD-ACT-QUARANTINE-01-1729252800000`)
  - `actor` (e.g., `Dr. Elena Vance (QA Food Safety Lead)`)
  - `action_type` (e.g., `ACTION_STATUS_CHANGED`)
  - `details` (e.g., `Status transitioned from PROPOSED to APPROVED: Authorized batch quarantine`)
  - `is_simulation: true`

### C. Simulation Guardrails & Regulatory Truthfulness
- **Simulated Execution**: All actions are explicitly marked and treated as simulations.
- **Guardrail Banner**: Prominently displayed across all views:
  > *"Simulated actions only. Nothing real is stopped or sent. Production warehouse management systems (WMS) remain unaffected."*
- **No External Side Effects**: The system does NOT send real supplier emails, initiate genuine recalls, halt real warehouse carriers, or transmit data to regulatory authorities.

### D. Persistence & Idempotency
- **FalkorDB Node Representation**:
  - `(:Action {action_id, title, action_type, target_type, target_id, status, initiator, path_classification, updated_at})`
  - `(:AuditEvent {event_id, timestamp, action_type, outcome, entity_id, actor, details, is_simulation})`
- **Restart Survival**: Restarting the FastAPI service without resetting FalkorDB preserves all action statuses and audit history.
- **Retry Safety**: All persistence writes use Cypher `MERGE` semantics, ensuring duplicate requests from network retries or double-clicks do not create duplicate nodes or corrupt status.

## 3. API Surface

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/api/actions/plan?raw_lot_code=...` | Returns the data-driven containment action plan for a lot with evidence lineage and audit trails. |
| `POST` | `/api/actions/item/status` | Updates the status of a specific action item (`PROPOSED`, `PENDING_REVIEW`, `APPROVED`, `REJECTED`, `COMPLETED`) with mandatory human actor and rationale. |
| `GET` | `/api/actions/export?raw_lot_code=...` | Generates a compliant FSMA 204 containment action plan dossier in Markdown format. |
| `POST` | `/api/actions/execute` | Executes simulated containment for an entire plan, recording audit events for all approved items. |

## 4. User Experience & Design Tokens

Built strictly to the Google Stitch Action Plans specification:
- **Canvas**: Warm parchment (`#FAF6EC`)
- **Cards & Surfaces**: Clean white (`#FFFFFF`) with subtle warm border (`#E4DFC9`)
- **Brand & Primary Actions**: Forest teal (`#337A68`)
- **Text**: Spruce deep green (`#24332F`) and muted slate (`#6E7B78`)
- **Semantic Badges**:
  - Simulated: Muted forest pill (`rgba(51, 122, 104, 0.08)`)
  - Confirmed Path: Coral alert (`#E77861`)
  - Evidence Gap: Purple / Sage review indicator
- **Responsive Viewports**:
  - **Desktop (1440x900)**: 2-column layout with left action backlog (380px) and right detail view.
  - **Tablet (820x1180)**: Fluid single-column stacked layout.
  - **Mobile (390x844)**: Responsive compact stacked view with accessible touch targets.
